设计理念符号系统
定义：
外延的符号：
若X是一个概念，则Ext(X)表示X的外延。
封装的定义：
若f: Ext(X)→Ext(Y)，则称概念X相对于概念Y在映射f上是封装的，即X□(→┴f封装 ) Y（可以这么理解：用f封装X，然后把用f封装后的X交给Y）。
映射系统的定义：
映射系统首先是一个系统，其中有3个要素：第一个是环境条件X这个概念；第二个是导向映射f这个映射；第三个是导致的全局状态Y这个概念。其中X□(→┴f封装 ) Y。记S=<X,f,Y>。
某映射系统实现了某效果的定义：
对于任意映射系统S和任意效果E，若S导致的全局状态的外延⊆E导致的全局状态的外延，则称S实现了E。
公理：
(1)：任何可设计系统都是一个映射系统。
(2)：越真善美的可设计系统越优秀。
(3)：对于三要素相同的两个系统S=<X,f,Y>与T=<X,f,Y>，若S的熵比T的熵更低，那S比T更真善美。（“追求导致外部假恶丑的系统其内部更无序那它能维持的时间越少而更真善美”这样之类的反驳是不成立的，因为系统其能维持的时间也算进三要素之内的话那不管怎样都是熵越低越有序越真善美了）
定理：
1：一个更优秀的实现了效果E的映射系统A，其必然满足以下必要条件：
(1)：A的环境条件X□(→┴A的导向映射f封装 ) E导致的全局状态G。
证明：如果想让映射系统A实现效果E，则需要让A导致的全局状态的外延⊆E导致的全局状态的外延，而因为
A的环境条件X□(→┴A的导向映射f封装 ) A导致的全局状态Y
，所以f: Ext(X)→Ext(Y)，而Ext(Y) ⊆E导致的全局状态G的外延Ext(G)，所以f: Ext(X)→Ext(G)，即X□(→┴f封装 ) G，或者说A.X□(→┴(A.f封装) ) E.G，即A的环境条件X□(→┴A的导向映射f封装 ) E导致的全局状态G。
(2)：脑海中有构建一套真善美的实现了效果E的映射系统A’=<X’,f’,Y’>，并且有尽量让A’中有的(模式)A中也有，A’中没有的(模式)A中也没有的痕迹。
证明：在让可设计系统S=<X,f,Y>实现效果E时，如果想让设计（比如编程）的可设计系统更优秀，则需要让设计的系统更真善美，为了善，需要让认知成本降低，不管是单人还是多人的设计，根据上述可知，应该先在脑海中构建一套真善美的实现了效果E的映射系统S’=<X’,f’,Y’>，然后尽量让S’中有的(模式)S中也有，S’中没有的(模式)S中也没有。
(3)：设E导致的全局状态为G，在让可设计系统A 实现效果E时，当已有可设计系统S=<X,f,S.Y>和T=<T.Y,g,G>时，有X□(→┴f封装 ) S.Y和T.Y□(→┴g封装 ) G,这时候有X□(→┴(g∘f封装) ) G⟸S.Y⊆T.Y，所以想要构造A=<X,g∘f,G>实现效果E的话请务必保证Ext(S.Y)⊆Ext(T.Y)，如果不成立的话请务必调整S和T使其成立。
(4)：对于可设计系统为代码系统的情况，当已有可设计系统S=<X,f,S.Y>和T=<T.Y,g,G>时，系统S和系统T可以视为脑海中有的模式，在文件夹目录中平级放置S和T的包，因为由S和T组成的系统A=<X,g∘f,G>可以视为脑海中有的(模式)，则需要一个装配图，比如一个JSON文件，设计为S和T同层级，A在S和T的上层将S和T包含在内或者其它装配方式。对于其它类型的可设计系统也是同理。
(5)：其是更真善美的。
设计原则是：
1：设计必须遵循该设计理念符号系统中体现的所有设计理念。
2：设计必须遵循公理(1)(2)(3)中对更优秀的可设计系统的要求。
3：要做满足定理1中提到的必要条件的更优秀的可设计系统。
4：经验总结出来的设计原则：用实在的东西把不实在的东西转化为实在的东西。
5：经验总结出来的设计原则：对于可设计系统为代码系统的情况，所有function在不违反其它设计原则的前提下尽量都：统一无返回值，在定义点和调用点的参数列表中用“/*->*/”等可以塞进参数列表的注释分开入参和出参，左边是入参（非只写入的），右边是出参（非只读取的）（必然注入的缓冲区），然后这样参数列表就可以只需要一行代码，而且还可以有DPS（Destination-Passing Style）式编程注释（这里的话是提到的“/*->*/”）。至于python，要是没那么严格的话（比如伪代码或者不需要发布的代码）就在入参和出参中间插入一个参数，定义点是定义参数“_: "->"”，通过类型注解实现DPS式编程注释，调用点是传入参数“"->"”，通过用不到的字符串参数实现DPS式编程注释。然后如果function是面向对象的方法并且这个面向的对象是出参的话，那改为左边是出参、右边是入参，“->”改为“<-”，如果这个面向的对象不是出参的话就不要改（阅读的时候可以将“=”视为特殊的“<-”），比如一个类有一个属性y，这个类有一个方法f(x, z)：y=x+1;z=x+1，调用后这个类的实例的属性y变成x+1，传入的z变成x+1，那么这个方法f(x, z)应该写为f(z /* <- */, x)，但是如果f(x, z)：z=x+1的话，那这个方法f(x, z)应该写为f(x /* -> */, z)。另外，对于原地读取并修改的对象，其既是入参又是出参，要同时在参数列表的入参侧和出参侧都放一个参数，调用时这两个参数位都传入同一个的该参数，由于大部分编程语言不支持function定义点的参数列表写同名参数，所以采用该对象入参的参数名为原名，出参的参数名为原名加“_self”后缀（如“x_self”，允许随编程语言的风格的不同而不同，比如在驼峰命名风格的语言中可以写作“xSelf”），并且将原名和原名加“_self”后缀这两个参数视为同一个变量的约定，禁止在调用点在这两个参数位传入除了null之外（因为function可能对于某些参数可以选择读取或者不读取、写入或者不写入，这时候只用bool标志来决定是否读取或者写入就会导致实际上不读取或者不写入了但是仍然传入非null对象的实际上违背设计原则的情况，所以允许传入null来表示这时候没有这个参数位）的两个不同变量，禁止在function的算法中假设这两个参数指向除了null之外的不同对象，二者必须始终视为同一对象的两个访问位（除了传入null之外），并且function内部只读取的对这个对象的引用只使用原名（入参名）进行读取，只写入的对这个对象的引用只使用“_self”后缀出参名进行写入，既读取又写入的对这个对象的引用优先考虑使用入参名进行读写，如果条件不允许的话再使用出参名进行读写。至于其它编程语言，同理处理。对于其它类型的可设计系统也是同理。
